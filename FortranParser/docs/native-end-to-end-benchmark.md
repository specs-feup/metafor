# Native Fortran parser end-to-end benchmark

This opt-in benchmark compares the local JSON and protobuf Flang plugins through the Java parser, graph reader, `FortranAstBuilder`, and `FortranNode.getCode()`. It does not change parser selection: the normal `FortranNativeParser` constructor still uses the JSON dumper.

## Run

From the Metafor checkout root, set the local dependency and Flang paths. The plugin paths below identify the finalized JSON module and its matching protobuf sibling used for this measurement:

```sh
export SPECS_JAVA_LIBS_HOME=/home/lmsousa/Documents/Projects/SPeCS/master/specs-java-libs
export FLANG=/tmp/flang22-libflang.woWtRQ/extracted/usr/lib/llvm-22/bin/flang-22
export JSON_PLUGIN=/tmp/flang22-libflang.woWtRQ/seqcst-fix/DumpASTPlugin.seqcst.so
export PROTOBUF_PLUGIN=/tmp/flang22-libflang.woWtRQ/seqcst-fix/DumpASTProtobufPlugin.seqcst.so
export LD_LIBRARY_PATH=/tmp/flang22-libflang.woWtRQ/extracted/usr/lib/x86_64-linux-gnu:/tmp/flang22-libflang.woWtRQ/extracted/usr/lib/llvm-22/lib

python3 FortranParser/scripts/benchmark-native-end-to-end.py \
  --flang "$FLANG" \
  --json-plugin "$JSON_PLUGIN" \
  --protobuf-plugin "$PROTOBUF_PLUGIN" \
  --repeats 5 \
  --warmups 1 \
  --output FortranParser/docs/native-end-to-end-benchmark-report.json
```

The runner builds the parser and writes `FortranParser/build/benchmark/end-to-end-classpath.txt` through the `writeEndToEndBenchmarkClasspath` Gradle task. It then invokes the Java entry point directly, outside the Gradle process, with `-Xms256m -Xmx1g` for both modes.

Before collecting measurements, the runner compares generated-code byte counts and SHA-256 hashes from the JSON and protobuf modes for all workloads. A mismatch stops the run before timed repeats. The workloads are `hello.f90`, PolyBench `3mm.f90`, and the deterministic 512-assignment source generated by the runner using the same source recipe as the native protocol benchmark.

Each timed sample uses a fresh JVM, runs one unreported full-pipeline warmup in that JVM, and records one sample. There are five samples per mode and workload; which protocol runs first alternates across repeats. Reported medians are ordinary medians of those five samples. The benchmark applies no automatic pass/fail performance threshold.

## Measurement scope

- `parse_nanos` covers `FortranNativeParser.parse()`: process launch, Flang execution, stdout consumption, JSON/protobuf decoding, and `FortranJsonResult` construction. Flang writes to a pipe while Java consumes it, so producer and reader work overlap. The reader-only duration cannot be recovered by subtracting Flang wall time.
- `ast_build_nanos` measures `FortranAstBuilder.build()`.
- `get_code_nanos` measures the returned root node's `getCode()`.
- `end_to_end_nanos` is a direct `System.nanoTime()` interval around those three stages in one JVM invocation.
- `java_process_vm_hwm_kib` is the Java process's own `VmHWM` value from `/proc/self/status`. The harness reads it after JVM startup, the in-process warmup, and the measured full-pipeline sample. It excludes child processes. If Linux `/proc` is unavailable, the report uses `null` and records an unsupported status.
- GNU `time` records elapsed time and `%M` for the Java command and each Flang command. These `%M` values are named `*_gnu_time_wait_rusage_maxrss_kib`, not process-only peaks. GNU `time(1)` says its resource values come mostly from `wait3(2)`. Linux `wait4(2)` returns resource usage for the waited child, and `getrusage(2)` describes `RUSAGE_CHILDREN.ru_maxrss` as the largest child RSS, not a process-tree maximum. A local check here reported 75,264 KiB from GNU `time %M` while the timed Python parent reported `VmHWM` of 12,072 KiB after waiting for a child that allocated 64 MiB. This confirms that `%M` can reflect waited-child memory; it is not a Java-only peak.
- Keep Java `VmHWM` and GNU `time` wait-rusage values separate. They cover overlapping work and must not be added.
- Generated-code equality is a migration gate for this benchmark; it does not establish semantic correctness or compile the generated source.

The JSON report pins the Git `HEAD`, dirty paths, source and synthetic-input hashes, schema and harness hashes, Flang and plugin module hashes, JVM settings, and the local library path. It preserves the Java-only `VmHWM` separately from Java-command and Flang-command GNU `time` wait-rusage values. Keep the report alongside the harness changes so the measurements remain tied to their exact inputs.

## Results

The current run's machine-readable measurements and medians are in [native-end-to-end-benchmark-report.json](native-end-to-end-benchmark-report.json). The report preserves stage durations, Java and Flang process peaks, code-equality preflight results, and the complete provenance record.

All three generated-code equality preflights passed. Each median below comes from five fresh JVM samples per mode, with one in-JVM warmup per sample.

- `hello.f90`: end to end was 105.102 ms for JSON and 105.264 ms for protobuf (+0.2%). Parse was 102.286/102.652 ms, AST build 2.200/2.064 ms, and `getCode()` 0.586/0.527 ms.
- PolyBench `3mm.f90`: end to end was 139.389/165.003 ms (+18.4%). Parse was 123.181/150.038 ms, AST build 10.935/11.406 ms, and `getCode()` 5.422/5.620 ms.
- Synthetic 512-assignment chain: end to end was 206.025/317.493 ms (+54.1%). Parse was 177.007/283.133 ms, AST build 22.664/29.182 ms, and `getCode()` 5.642/6.273 ms.

The Java process's own median `VmHWM` was 104.0/106.4 MiB for JSON/protobuf on `hello`, 125.2/132.8 MiB on `3mm`, and 210.3/225.0 MiB on the synthetic input. GNU `time %M` for the timed Java command reported separate wait-rusage medians of 104.3/106.8, 125.5/133.3, and 210.7/225.7 MiB. The Flang-command GNU `time %M` wait-rusage medians were 102.2/94.4, 106.2/99.2, and 104.0/98.6 MiB. Do not add these metrics. GNU `time %e` is reported to hundredths of a second; Flang-command elapsed medians were 0.03/0.03 s, 0.04/0.06 s, and 0.06/0.15 s.

Protobuf did not improve Java end-to-end latency or Java `VmHWM` in these runs. The small fixture was effectively tied, while protobuf took 18.4% longer on `3mm` and 54.1% longer on the synthetic input. Its Flang-command GNU `time %M` values were lower, but those wait-rusage figures are a separate measurement and do not offset the reader-path slowdown. These results cover the three listed inputs and this local build. They do not establish general performance or semantic correctness, and they do not select a default parser.
